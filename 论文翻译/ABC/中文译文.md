# 构建严谨 Agent 基准测试的最佳实践

**英文题名：** Establishing Best Practices for Building Rigorous Agentic Benchmarks  
**作者：** Yuxuan Zhu 等。  
**原稿：** 41 页。本文保留方法名称、评价代号、数值、引文标号及源代码标识。

> **译文范围提示：** 以下为论文摘要和主文核心章节的中文译文与按原文组织的技术译述，并非 41 页逐句译本。英文逐页全文、全部附录、参考文献和原稿页图单独保留；未译内容不标记为“已译”。

## 摘要（全文翻译）

基准测试对于定量跟踪人工智能的发展至关重要。随着 AI 智能体能力不断增强，研究人员与实践者开始提出智能体基准测试（agentic benchmarks），以评价智能体完成复杂现实任务的能力。这些基准通常通过特定的奖励设计对任务结果评分，从而衡量智能体能力。然而，我们发现，许多智能体基准在任务配置或奖励设计方面存在问题。例如，SWE-bench-Verified 采用的测试用例不足，而 τ-bench 将空响应计为成功。这些问题可能造成智能体性能的相对高估或低估，幅度最高达到 100%。为使智能体评估更加严谨，我们提出 **Agentic Benchmark Checklist（ABC，智能体基准测试检查清单）**，将团队构建基准的经验、最佳实践调查及已报告的问题综合为可操作的指导原则。将 ABC 用于评估设计特别复杂的 CVE-Bench 后，性能高估幅度下降了 **33%**。

## 1 引言

随着智能体开始结合模型、工具、记忆与外部知识解决现实问题，评价其能力与风险的基准测试日益重要。然而，智能体基准测试明显比传统分类或固定输出任务更加复杂。首先，智能体输出常常是自由文本、代码、命令执行结果或者环境状态变化，无法仅通过固定类别标签判断正误。其次，真实任务依赖浏览器、操作系统、数据库和外部 API 等复杂环境；环境设计本身就可能产生漏洞或不稳定因素。因此，分数是否准确反映智能体能力，必须经过独立验证。

作者指出，**SWE-bench-Verified 的测试集可能无法覆盖补丁的关键边界情况**，导致错误补丁通过测试；在 τ-bench 的某些本来不可完成的任务中，“保持环境不变”被视为成功，因而什么都不做的智能体也可能得到较高分数。论文报告，该简单策略在 τ-bench 的相关实验中达到了 **38% 成功率**，足以说明“通过检查”不必然等同“具备目标能力”。

论文围绕两个必要条件建立评价框架：**任务效度（Task Validity）**及**结果效度（Outcome Validity）**。基于这些条件，作者设计 ABC，对不同类型的智能体基准进行审计，并讨论结果报告的透明度。研究不仅报告已有缺陷，也试图让后续基准开发者能够在发布前逐项检查和修复问题。

## 2 相关研究

已有基准研究关注标注质量、标签噪声、统计有效性、污染、可复现性和实际使用等维度；但许多研究围绕选择题或常规生成任务展开，对多轮工具调用及交互环境的覆盖不足。现有智能体基准涉及软件工程、网络操作、安全测试、环境交互和数学推理等，其中任务具有多步骤执行与非结构化输出的共同特点。此前的研究已揭示 SWE-bench、BIRD、KernelBench、WebArena 等系统中的个别缺陷，但缺乏统一、可执行、跨类型的审计清单。ABC 试图弥补这一空白。

<details><summary>英文原始标题（点击展开）</summary>

Figure 1: Operational and conceptual processes of agentic evaluation. An agentic benchmark measures the capability of AI agents via agentic tasks. It determines the success of a task by evaluating the task outcomes. Establishing task validity (e.g., equivalence between the target capability and the task success) and outcome validity (e.g., equivalence between the task success and positive evaluation results) are keys to ensure rigorous agentic evaluation.

</details>


一个基准首先设置任务、工具和环境，由智能体执行后产生任务结果；评价器再将该结果转换为成功或失败。因此必须分别检查两个映射：

1. **任务效度**：成功完成任务是否真正意味着具备待测能力？反之，具备能力的智能体是否能够完成任务？无解题、答案泄露、可投机的环境状态都可能破坏这一对应关系。
2. **结果效度**：评价器给出通过结果，是否真的代表任务完成？正确完成的任务能否被评价器识别为通过？测试不足、过度严格的字符串匹配、遗漏允许状态等都会破坏这一对应关系。

论文特别强调两种危险来源。**复杂任务环境**可能提供与能力无关的捷径，也可能使任务实际不可解；**非结构化任务结果**使自动打分必须依赖解析器、字符串比较、单元测试、模糊测试、状态匹配或模型裁判，而这些评价器本身也可能出错。作者梳理了 17 个具有代表性的智能体基准，选择其中 10 个进行 ABC 评估；对清单每项满足记 1 分，否则记 0 分，并以实验进一步验证发现的问题。

### 4.1 任务效度：工具、环境与实现

![图2：ABC 中的任务效度检查项目](./images/figure-02-p005.png)

下表依照原论文图 2 保留了检查项代码，便于在真实 Benchmark 审计中复用。

| 编号 | 中文检查要求 |
|---|---|
| T.1 | 明确说明所用工具及依赖版本，例如 Python 或 GIS 库版本。 |
| T.2 | 评价过程中所需 API 工具能够持续访问。 |
| T.3 | API 不可用时能够正确终止任务或处理错误。 |
| T.4 | 不同评测运行之间彻底清除残留数据与环境状态。 |
| T.5 | 智能体与标准答案、评价器内部信息充分隔离。 |
| T.6 | 环境设置不随时间漂移，避免依赖动态更新的网站。 |
| T.7 | 人工标注的 Ground Truth 已验证正确性。 |
| T.8 | 逐个确认测试任务客观上可以完成。 |
| T.9 | 提供可自动完成所有题目的 Oracle Solver，以验证任务配置。 |
| T.10 | 实现不存在无需完成任务就能通过评估的漏洞。 |

工具部分区分自托管工具和第三方 API：前者尤其要固定版本，后者要关注限流、中断和服务可用性。环境部分要求跨任务状态重置、信息隔离和可复现。实现部分要求核对标准答案与任务可解性，并推荐提供自动 Oracle。作者以 KernelBench 中 GPU 内存残留标准答案、τ-bench 中无需采取行动即可成功等案例说明问题的重要性。

### 4.2 结果效度：如何核实任务结果


**原论文图3：ABC 中的结果效度检查项目（PDF 第 6 页）**

![图3：ABC 中的结果效度检查项目](./images/figure-03-p006.png)

<details><summary>英文原始标题（点击展开）</summary>

Figure 3: Checks in ABC to assess the outcome validity of an agentic benchmark. We group items by the types of the outcome and the methods of evaluation.

</details>


**信息获取与文本答案。** 对于完整字符串匹配，需允许与标准答案语义等价的表达，处理回答中的合理冗余；对于子串匹配，应正确理解否定词、防止枚举所有候选答案的投机行为，并避免过于简单、可随意猜中的 Ground Truth；使用 **LLM-as-a-Judge** 时应提供裁判准确率、一致性及人类一致度的证据，并抵抗对抗性输入及奖励投机。原文对应检查项为 O.a.1–O.a.2、O.b.1–O.b.3 和 O.c.1–O.c.2。

**代码生成与测试。** 单元测试或端到端测试需要验证测试用例本身的正确性，并通过覆盖率、圈复杂度等客观指标检查测试质量（O.d.1–O.d.2）。模糊测试（Fuzz Testing）应覆盖边界输入、数据类型、内存布局和不同取值范围，还应确保随机输入确实能影响被测函数输出（O.e.1–O.e.3）。端到端测试还须覆盖相关执行分支，并避免测试结果因随机性或环境因素波动（O.f.1–O.f.2）。

**环境状态修改。** 对于预订、网站修改等状态变化任务，正确的最终状态可能不止一种。因此 Ground Truth 需要覆盖所有合法成功状态（O.g.1）；既检查应改变的状态，也检查不应被改变的状态（O.g.2）；还要让目标状态足够复杂，以避免随意修改轻易通过（O.g.3）。

**多步推理。** 若采用答案匹配，应在题目中明确输出格式及解析器假设（O.h.1），并降低随机猜对的可能性或报告随机基线（O.h.2）。若采用自定义质量指标，应确认高分确实对应任务目标，避免为了优化得分而偏离实际任务（O.i.1）。

原文图 4 的报告清单可概括为三组：

| 编号 | 中文检查要求 |
|---|---|
| R.1 | 至少部分开放数据或基准实现。 |
| R.2 | 提供公开的评测执行框架（evaluation harness）。 |
| R.3 | 采用措施避免测试数据污染，例如未公开保留集。 |
| R.4 | 有持续更新任务、避免过拟合的安排。 |
| R.5 | 设立维护和接收改进反馈的机制。 |
| R.6 | 明确目标智能体能力与被测构念/结果的关系。 |
| R.7 | 明确评估对象是模型本身还是完整智能体系统。 |
| R.8 | 报告预防、检测及修正缺陷的具体措施。 |
| R.9 | 定性讨论无法消除的评价缺陷造成的后果。 |
| R.10 | 定量评估不可避免的缺陷对分数的影响。 |
| R.11 | 报告置信区间或其他统计不确定性指标。 |
| R.12 | 说明在存在缺陷时应如何解读评分。 |
| R.13 | 报告人类专家等非 AI 基线。 |
| R.14 | 报告不做任务等平凡智能体基线。 |

作者指出，某些评估误差不能彻底消除，尤其是使用模型裁判、含有噪声的 Ground Truth 或复杂程序测试时，更应公开限制及其潜在影响。**不完整但明确限定的评价结果，比形式上精确而缺乏限制说明的单一排行榜分数更可取。**

作者评估的 10 个基准涵盖软件工程、信息获取、交互环境及安全等能力，分别使用单元测试、模糊测试、状态匹配、字符串匹配、答案匹配等打分方式。图 5 汇总了三类清单分数。结果显示：**7 个基准有任务效度问题、7 个有结果效度问题，10 个都存在报告方面的局限。**

实证发现包括：

- **τ-bench**：某些任务的目标就是保持环境不变，导致不执行操作的智能体获得 **38%** 的相关评分；另有子串匹配问题，使枚举答案的策略产生约 **40%** 的高估。
- **WebArena**：子串打分忽略多余内容；对于标记为 N/A 的任务，模型裁判可能接受空回复，论文实验报告性能高估约 **1.4%–5.2%**。
- **SWE-Lancer**：测试与智能体不充分隔离，智能体可能操纵测试文件，出现不完成任务也达到 **100%** 得分的漏洞。
- **KernelBench**：模糊测试没有充分覆盖边缘情形与内存布局，正确性表现可能被高估约 **31 个百分点**。
- **OSWorld**：外部网站更新导致 HTML 选择器失效，论文报告 Chrome 任务子集性能低估约 **28%**。

这些案例不应被理解为对应智能体能力一律较差，而是说明**测量程序可能把任务成功与得分成功混为一谈**。作者随后把 ABC 应用于 CVE-Bench 的开发，展示在发布阶段进行检查与修复如何减少虚高分数；论文报告性能高估减少 **33 个百分点**（相关表述以原稿上下文为准）。

## 6 结论与局限

论文主张，将基准本身当作需要验证的测量工具，而不是默认真实的“标准答案机器”。**任务效度、结果效度、报告透明度**是维护其可信度的三个支点。对基准进行审计时，不仅要检查单题 GT，还应检查环境隔离、工具稳定性、解析器、测试覆盖率和投机基线。

作者也承认，清单不能覆盖所有未来的评价形式，部分标准难以完全量化，且现实环境可能有无法彻底消除的随机性。应用 ABC 时仍需保留具体领域背景、人工审查和结果不确定性分析。
