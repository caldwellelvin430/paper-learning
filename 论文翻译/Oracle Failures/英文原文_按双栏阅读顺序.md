Abstract

Agent evaluation harnesses are software: they run a test suite, drive a test input
generator, and decide outcomes with a test oracle. We audit them for defects a
score table cannot show.
First, a systematic oracle-integrity auditing approach — five state-
integrity invariants and three known-answer controls — is measured by injecting
seven oracle defect classes across two task domains and a synthetic domain.
Every class is detected, and on the 57 separable variant–target combinations it
detects 54; the repaired oracle yields no false positive. On a widely used agent
benchmark, it exposes a reward function that resets the database to build a
ground-truth hash and never restores it, so a harness scoring afterwards reads
the reference solution’s state: recorded labels report 4,194 database passes over
4,320 episodes, replay gives 2,883, and success falls from 94.3% to 65.5%. The
correction is not a uniform oﬀset; it removes 24 to 34 points from each agent and
changes which agent this matrix measures as strongest.
Second, more weakly, localising the apparatus is a property of the measurement:
a 3,240-episode ablation associates the three documents with lower collapse in the
tested configuration, without ordering them, and a second task domain reverses
the language eﬀect.
Third, the method did not transfer to a second, independently implemented
benchmark; we name the contract required. A replication package recomputes
every analysis offine with no model calls.

Keywords: test oracle, flaky tests, measurement validity, benchmark quality,
replication package, LLM agent evaluation

1 Introduction

Evaluating an AI agent means running it against a benchmark and reporting the
number that comes out. That number — a success rate — is what a paper states,
what a leaderboard ranks, and, increasingly, what a deployment decision rests on. It
is not produced by the agent alone. It is produced by an evaluation harness: a suite of
test cases (the benchmark’s tasks), a generator of test inputs (increasingly a language-
model user simulator), and a test oracle — the benchmark’s reward function — that
decides whether each run passed. The harness is software, and the score is one of its
outputs (Figure 1).
Software engineering has spent decades on the failure modes of exactly this
arrangement. Deciding expected from actual is the oracle problem, and it is where test
suites fail most quietly (Barr et al, 2015). A test that passes and fails on unchanged
code is flaky (Luo et al, 2014). A measurement that moves when the apparatus
changes, while the property being measured does not, is a validity failure rather than a
capability diﬀerence (Kitchenham et al, 2002). Fault injection, in the lineage of muta-
tion testing (Jia and Harman, 2011), is the standard way to ask whether a test suite
would notice a defect at all. These are settled methods with an unsettled application
area.
Agent benchmarks have adopted the software without adopting the methods. In
particular, a benchmark’s reward function is treated as definitional: it defines what
success means, so it is not itself tested. Two consequences follow. First, an error inside
the oracle is invisible by construction, because the oracle is the instrument that would
have detected it, and because the returned value can be correct — the defect can
be in what reading the oracle leaves behind. Second, because the harness is also how
a configuration is expressed (which language the simulator speaks, what the agent’s
policy and tool descriptions say), a change in the apparatus is read as a change in the
agent. Neither consequence is hypothetical: this paper reports one instance of each,
found by auditing one widely used agent benchmark.
We therefore treat the evaluation harness as a system under test and audit it. We
organise the work as three questions, of which only the first is about the evaluation
system itself; the other two are analyses of the measurement process, and we state
them at that strength.
RQ1 (primary). How reliable is the evaluation oracle — would it notice a defect
in itself, and does it have one? The object of study is the evaluation system: the
correctness and consistency of its verdicts and the fidelity of the labels it produces.
The evidence is a test suite aimed at the oracle and a fault-injection battery aimed
at the harness.
RQ2 and RQ3 (secondary). How do harness configurations influence observed
evaluation outcomes, and how sensitive are the conclusions to factors that vary during
execution? These are analyses of the measurement process, run on the same audited
pipeline. Their object is not the model: we do not set out to characterise intrinsic
language-model capability or behaviour. What they characterise is how design choices
in the harness — which documents are localised, which task domain is used — expose,
amplify or obscure variability that is present while a benchmark runs, and where the
resulting conclusions stop holding.

Contributions.
1. A systematic oracle-integrity auditing approach, with sensitivity and
specificity measured on the implementations studied. Eight checks in two
families — five state-integrity invariants and three known-answer controls — plus
a fault-injection battery of seven defect classes and a ground-truth-controlled syn-
thetic domain. Validated across three targets; every injected defect class is detected,
with no false positive on the repaired oracle the package ships, and each class maps
to a minimal detector (Section 3.2). At the variant level the suite detects 54 of
the 57 separable variant–target combinations, and the three misses are the same
variant on each target, named rather than summarised away (Section 4.1).
2. An oracle defect found by that method, a minimal reproduction, and
a replay-based correction. The benchmark’s Env.calculate_reward() resets
the environment database to build a ground-truth hash and never restores it. The
value it returns is correct: it is computed from a hash taken before the reset, and
the benchmark’s own agent consumes that value without reading the environment
again, so the benchmark’s own runner is unaﬀected. It becomes a wrong label only
because our harness scores the episode separately, after the session has ended, and
therefore re-reads an environment left holding the reference solution. We report this
as an integration failure and assign it as one — the unsafe side eﬀect is upstream,
the second reading is ours — and make no claim that the upstream runner inflates
its own success rates. On 4,320 episodes the archived labels record 4,194 database
passes; replaying the recorded tool calls against a clean database gives 2,883, and
success falls from 94.3% to 65.5% (Section 4.1). The change is not a uniform oﬀset:
it diﬀers across agents by enough to reorder the top of this matrix, so the defect
distorts comparisons between systems and not only the absolute score (Section 4.1).

2 Background and Related Work

2.1 Test oracles, mutation testing and the oracle problem

Deciding expected from actual is the oracle problem, a foundational difficulty of soft-
ware testing (Barr et al, 2015). The trouble is not that oracles are absent but that
they are unexamined: an oracle is exercised by every test run and tested by none, so
its own faults are silent. Mutation testing grew out of this observation (Jia and Har-
man, 2011) — inject a fault, then ask whether the suite notices — and remains the
standard technique for measuring what a test suite can actually detect. We take that
technique and point it at the oracle itself rather than at the program under test.
Two properties of an oracle make our variant distinct. First, it can be stateful:
an oracle that re-derives its expectation by replaying a reference solution against a
live database can return a correct value and still leave the system in a state no other
reader expects. Second, its contract with the harness is usually implicit — who reads
the environment, and when, is not specified anywhere — so a second reader can be
wrong through no fault of the oracle’s own runner. Our first contribution is a state-
integrity formulation of the oracle problem for machine-learning evaluation harnesses,
together with the fault-injection battery that measures it.

2.2 Flaky tests, measurement validity and configuration
sensitivity

A flaky test passes and fails on the same code (Luo et al, 2014). In empirical software
engineering the same worry appears as measurement validity: a reading that responds
to the apparatus rather than to the property under study is not a weaker measure-
ment of that property, it is a measurement of something else (Kitchenham et al, 2002).

Metamorphic testing approaches the difficulty from a third direction, checking rela-
tions that must hold between related inputs when a direct oracle is unavailable (Chen
et al, 2018).
Our second contribution sits between these three, and it needs one distinction
that the flakiness literature does not supply. Changing the language of the apparatus
changes the input the agent receives: the simulated user now writes Chinese, or the
policy, the tool descriptions and the error strings are read in Chinese. An agent may
legitimately behave diﬀerently, so a diﬀerence in outcome is not by itself evidence
that the oracle is defective, and we do not read it as one. The validity question arises
one step later, when such a diﬀerence is attributed to the system under test — a
capability claim, a leaderboard position — while the measurement contract holds the
apparatus fixed. Our secondary experiments are therefore reported as configuration
dependence of the observed outcome and bounded to the configuration in which they
were measured; what the component ablation manipulates is the set of documents
that name the same objects, tools and error conditions in another language. In agent
evaluation the analogous instability also has a level that CI flakiness does not: the
trajectory, where a model’s multi-step behaviour degenerates non-deterministically
rather than the same test returning two verdicts.

2.3 Testing and evaluating LLM-based systems

A separate strand treats a language model as the system under test, asking how to
specify, exercise and judge a system whose outputs are not deterministic (Hou et al,
2024), (Zhang et al, 2022). We take that framing and apply it one level down. The
system under test in this paper is not the model but the evaluation harness: the
model is the input generator and the agent is the system the harness measures. The
distinction matters because the two are routinely conflated — a benchmark’s reward
function is treated as definitional rather than as software with failure modes — and
because a fault in the harness is invisible in precisely the way a fault in an oracle is.

2.4 Agent benchmarks and the reliability of their
measurements

Benchmarks are themselves software artefacts whose validity and reproducibility must
be argued rather than assumed (Recht et al, 2019), (von Kistowski et al, 2015). In
agent evaluation the argument has mostly proceeded by measuring the measurement’s
noise rather than by auditing its apparatus: model-as-judge scores vary with the judge
and the prompt (Yin, 2026), (Mahmood et al, 2026); rankings shift under resampling
or a change of reported statistic (Zheng and Yang, 2026), (Khosravi and Huo, 2026),
(Bjarnason et al, 2026); aggregate success hides what actually happened in a run
(Khanal et al, 2026); benchmarks can be answered without solving the task, or fail to
discriminate between systems that diﬀer (Kehkashan et al, 2026); and the apparatus
itself revisits established benchmarks (Yehudai et al, 2026), (Sierra Research, 2024),
(Barres et al, 2026). We share that concern and change its object: instead of asking
whether the score is noisy, we ask whether the instrument that produces it is correct,
using tests aimed at the instrument.

2.6 Replication and artefact evaluation

Studies of the kind this paper reports are judged as much on whether a reader can
rerun them as on what they found (Winter et al, 2022). Two conventions from that
practice shape what we release. First, a replication package should carry the frozen
inputs, not a recipe for regenerating them, because a recipe rerun months later repro-
duces a diﬀerent system. Second, a package should distinguish what it can check from
what it cannot: ours reports a per-source verification status and counts only sources
whose file was found and whose hash matched as verified, rather than treating an
absent archive as a pass. Both choices are recorded in the deviation log rather than
presented as the original plan.

3 Methodology

3.1 The evaluation harness as a system under test

The object of this study is not a model but the software that evaluates one, and the
mapping to testing vocabulary is direct. The benchmark supplies a suite of test cases:
tasks that specify a user’s goal and, for each, a reference sequence of tool calls that
satisfies it. The test input is generated at run time by a language model playing the
user. The system under test is a tool-calling agent — a model plus a fixed control
loop — and the test oracle is the benchmark’s reward function, which decides pass
or fail by comparing the terminal state of a database against the state the reference
actions would have produced, and by requiring that certain output strings appear
in what the agent said. The assertions are therefore two: a state comparison that is
language-neutral, and a substring match on the final reply that is not.
Two properties of this arrangement matter for what follows. The oracle is a func-
tion of mutable state: to construct its expectation it must execute the reference
actions, which means it must touch the same database it is grading. And the grading
is a two-component conjunction, which lets us separate the state component from the
textual one when the two disagree.

3.3 Benchmark, task suite and configuration space

We use a tool-use benchmark of the “agent–user–database” form, in two of its domains:
a retail domain, from which 30 of the test tasks were sampled for the pre-registered
matrix, and an airline domain, whose 50 test tasks are used in full. The airline domain
was added in a later round of the study and required a Chinese version of its task
instructions; that translation was produced by a model and then checked mechanically
— identifiers, ISO dates, flight numbers, airport codes present in the English text, and
every numeral must appear verbatim in the Chinese, and no Latin fragment absent
from the English may appear — with the residual limitation that semantic equivalence
rests on the mechanical check plus one reading pass, and not on a second independent
translator.

simulator writes. The environment language is the language of the three documents
the agent reads: its policy wiki, its tool descriptions, and the strings its tools return
on error. Database contents — names, addresses, order and product identifiers — are
never translated, because they are data rather than prompt, and enumerated literals
that a tool contract requires verbatim are kept in English inside the translated text,
so that a localised arm cannot fail through argument validation instead of through

3.4 Design and pre-registration

The pre-registered matrix varies the user language with the task, the agent, the sim-
ulator model and the repetition held fixed — 30 tasks × 2 languages × 6 simulators
× 4 agents × 3 repetitions = 4,320 episodes — and is analysed from the archived
episodes rather than regenerated. A second pre-registered factor crosses the user lan-
guage with the environment language, 1,080 episodes, plus 1,080 in the length-padded
environment. Three further experiments, whose designs were frozen before the corre-
sponding runs, were added in a later round of the study: a per-component ablation of
the environment factor (3,240 episodes), a repeat of the user-language manipulation
in a second domain (1,200 episodes), and an independent adjudication of the collapse
label (212 archived episodes).
Two arms were changed after their pilot data were seen, and we report this as
a deviation rather than presenting the final design as the planned one. The second-
domain experiment was to include a cross-vendor agent; its pilot collapsed in none of
120 episodes, so by the pre-registered stopping rule that arm was dropped, halving the
experiment and leaving independent-model validation open. The adjudication was to
draw 200 collapsed episodes; the archive contains 106, so it became a census. The pilot
itself was a directional check with a pre-registered decision rule, not a significance test.

3.5 Measurement and statistics

The unit of randomisation we care about is the task, so the primary inference is a task-
clustered interval: we aggregate the paired diﬀerence within each task, take the mean
across tasks, and use the t(G −1) reference distribution, with G the number of tasks.
Comparisons are paired within the same task, simulator, user language and repetition,
so that a component arm is compared with the baseline on cells that diﬀer in exactly
the manipulated component. Exact and permutation tests are reported, where they
appear, as cross-checks on an estimate and are never used on their own to declare
an eﬀect resolved. Every reported score is computed under the corrected grading
described in Section 4.1; where an archived arm’s labels required reconstruction, we
rebuilt the state component by replay and left the textual component as archived,
since the defect aﬀects only the former. An interval that contains zero is reported as
no detected diﬀerence.

4 Results

4.1 RQ1 (primary): How reliable is the evaluation oracle?

The suite and its validation.
We implemented the eight checks of Section 3.2 against an interface of four operations
— make a fresh environment, take a state signature, call the oracle, and name the
class the oracle lives in — and ran them on three targets: the oracle of a retail-
domain agent benchmark, the oracle of the same benchmark’s airline domain, and
a synthetic domain written from scratch. The first two are two task domains of one
scoring implementation, not two independent frameworks, and we do not claim more
than that; the second domain contributes a diﬀerent task suite, tool surface and
database against the same oracle code. The synthetic domain exists to show that the
suite is not shaped around one benchmark and to provide a ground-truth-controlled
setting. Throughout, three targets means these three.
For each target we injected seven defect classes, one at a time, into the oracle.
Table 3 gives the outcome.
Two summaries of the same run are possible, and they diﬀer. At the level of the
seven defect classes, every class is detected on every target. The battery is finer than
that: each class is realised by several concrete variants of the reward function, 21
variants in all, and running them against three targets gives 63 variant–target combi-
nations. On the primary denominator — the 57 combinations that a diﬀerential probe
showed to be behaviourally distinct from the shipped implementation, the remain-
ing 6 being left unresolved by the probes and never counted as equivalent — the full
suite detects 54 of 57. On the conservative denominator, which also counts the 6
unresolved combinations, it detects 56 of 63. We report both and do not mix them:
they answer diﬀerent questions, and the larger number is not the stronger result. The
headline of this subsection is the smaller number, because it is the one a reader can
check against the released fault matrix.
The identity of the un-injected baseline matters, and we state it explicitly because
the two sentences that follow would otherwise appear to contradict each other. The
implementation this suite audits is the copy the package ships, and that copy carries
the repair described below; the class labelled as shipped in Table 3 is therefore the
repaired implementation, and it passes every check on every target. The class labelled
state mutation is not a hypothetical: it is a faithful reproduction of the same function
before the repair, with no restore statement of any kind. Against that reproduction,
INV-5 fires on every task we sampled in both domains. A three-way check confirms

The miss, and why a class-level summary hides it.
Table 3 summarises the injection experiment at the level of the seven defect classes,

The suite is therefore not free of blind spots, and the miss is the same combination on
all three targets: an oracle that swallows an exception raised inside itself, so that INV-
4 records the probed path as not applicable rather than as a violation. The mechanism
is worth naming because it is not an accident of this implementation — a check whose
precondition is destroyed by the defect it is meant to detect will record that defect as
inapplicable. We report the miss rather than the class-level summary that conceals it.

Which checks are load-bearing.
The last column of Table 3 is computed rather than asserted. A check is necessary for
a class when removing it leaves some detected combination of that class undetected by
any remaining check; none means no single check is necessary, because two or more of
them independently cover the class. Four of the eight checks are necessary for at least
one class and four are not for any: INV-3 (9 unique detections across the battery),
CTL-1 (15), INV-4 (6) and CTL-3 (5), against INV-1, INV-2, INV-5 and CTL-2 with
zero. Redundancy is not a flaw in a test suite — an independent check that agrees is
how a suite earns trust — but it does mean the eight checks are not eight independent
capabilities, and the detector ablation in the replication package is computed on that
basis. The two families remain non-interchangeable: an oracle that is state-clean but
wrong is invisible to the invariants, and one that is state-dirty but accidentally right
is invisible to the controls.

What the suite found on the benchmark.
The benchmark’s reward function resets the environment database in order to replay
the reference solution and construct a ground-truth hash, and it never restores the
database afterwards. The value the function returns is correct, and the benchmark’s
own agent consumes that value without reading the environment again, so the bench-
mark’s own runner is unaﬀected. What turns the side eﬀect into a wrong label is a
harness that scores the episode separately, after the session has ended: the second read
finds the reference solution’s state rather than the agent’s. Our harness did exactly
that.

and it fires without any downstream code being involved: after a session-ending step

4.3 RQ3 (secondary): How sensitive are the conclusions to
execution factors, and where do they stop holding?

RQ1 and RQ2 report what the audit found. RQ3 reports where each of those answers
stops holding: the implementation boundary, at which the same auditing method failed
to transfer to a second, independently implemented framework; and the instrument
boundary, at which the criterion this paper relies on turns out to be an operational
definition corroborated by a language model rather than a human ground truth. We
report both as results rather than as omissions. The task domain is itself part of the
configuration, and we treat its eﬀect under RQ2 for that reason.

The implementation boundary.
We applied the same oracle-integrity suite to a second, independently implemented
agent framework. The attempt did not yield a validation. The reference terminal
state that the positive control needs cannot be reconstructed by an external harness
from that framework’s recorded API-call log, so no sensitivity or specificity could be
estimated on its held-out task set and we report none. The fixture the framework does
expose cannot serve as a positive control either: of its 21 held-out tasks, the three
that look usable are false positives produced by the same state-reconstruction defect
the control exists to detect. The constraint is contractual rather than incidental —
the framework materialises a reference episode only inside its own run loop — and we
state it as the precondition a framework must meet before this class of auditing can
be ported to it. Section 6 records it as the external-validity boundary it is.

An independent language-model adjudication reproduces the collapse label.
The collapse criterion is a mechanical operational definition, and a reader is entitled
to ask whether an independent judge would call the same runs degenerate. We put
every collapsed episode in the archive (106) together with a matched non-collapsed
control, masked the language arm and the criterion’s own intermediate quantities by
replacing each user turn with a placeholder, and had a judge from a diﬀerent model
family decide, blind to the hypothesis, whether the agent stops making progress. Of
212 items the judge returned a parseable verdict on 210 (0.9% attrition). Agreement
with the mechanical criterion is 98.1% (Wilson 95% [95.2, 99.3]), Cohen’s κ is 0.962,
sensitivity is 98.1% and specificity 98.1%.
The quantity that matters for this paper is whether the agreement diﬀers between
the language arms: 98.6% in the English arm (one discordant item) and 97.9% in the
Chinese arm (three discordant items). We did not observe a clear diﬀerence. That
is weaker than independence, and the distinction is what this subsection is about.
Agreement is at the ceiling, so the comparison has little power to detect a moderate
arm-dependent bias; the 212 items are the archive’s positives plus matched negatives
rather than a draw from a deployment distribution, so the reported sensitivity and
specificity are properties of that selected sample and do not transfer to a population
with a diﬀerent base rate; and the residual leakage is real — to judge whether the
agent stops making progress the judge must read what the agent said, and in the
Chinese arm those words are Chinese. We therefore claim that no clear dependence
of the criterion’s agreement on the arm was observed, not that independence was
established, and not that the judge is blind to language. The judge is also a language
model, not a person; this study has no annotator budget, so the criterion is reported
as an operational definition with independent corroboration rather than as a natural
kind.

5 Discussion

An evaluation oracle is software, and it needs the tests other software gets.
The defect we report is not exotic. A function that mutates the state it is grading
and returns without restoring it is the ordinary shape of a resource-handling bug;

19


---

## 原稿第 20 页

what makes it consequential here is that the function is the grader, and that its caller
had no reason to suspect it. The mechanism is a missing restore, not a partial one:
the function resets the database in order to replay the reference solution, builds the
ground-truth hash from it, and returns with the reference solution’s writes still in
place. A restore that happens on the success path but not on the failure path is a
diﬀerent defect; it is one of the injected variants in our battery (the class we label
exception leak), and it is not the defect the benchmark carried. Two checks in our suite
would have caught the benchmark’s defect immediately and cost nothing to run. The
repeat-scoring check — score the same finished episode twice and require the same
verdict — fails on the first call after the first, because the first call has already moved
the environment. The terminal-state check — after a session-ending step, assert that
the environment still holds the state the agent left — fails without any downstream
code being involved. Neither requires a reference implementation, a model call, or a
human. We suggest that both belong in the continuous integration of any harness that
grades an agent episode, next to the regression test that pins the fix.

What a cross-lingual score table does not say.
A score table reports a measurement. It does not report the instrument’s failure rate,
and our results are a case in which the instrument’s failure rate and the measurement
move independently: in the retail configuration the aggregate score diﬀerence is unre-
solved while the rate at which one agent’s trajectory degenerates roughly doubles, and
in the airline configuration the same manipulation moves the degeneration rate in the
opposite direction. A practitioner comparing two language configurations of the same
evaluation therefore cannot read the comparison as a statement about the model, and
cannot even assume the direction of the instrument’s bias is stable across task suites.
This is a claim about attribution, not about the oracle: a change of language can alter
what the agent does for reasons that have nothing to do with a defective grader, and
we do not infer a grader defect from a score that moved (Section 2.2). What makes
the comparison uninterpretable is that the score is attributed to the model while the
apparatus that produced it changed. Reporting an instrument-failure rate alongside
the score, and checking it in more than one task suite before acting on it, are the two
actions that follow.

Localisation is a configuration change, and it should be tested as one.
The practical reading of the component ablation is not that one document matters
and the others do not; it is that changing the localisation of an agent’s world changes
the reliability of the measurement, and that the change is spread over the parts of
the world the agent reads. A team that localises the user-facing side of an agent while
leaving its policy, its tool descriptions and its error vocabulary in English is running
a configuration whose measurement properties diﬀer from both the fully English and
the fully localised ones. Testing that configuration — rather than assuming it is an
intermediate point between the two — is what the ablation suggests.

Replay as the audit primitive.
The correction we report is not a re-run: the provider oﬀers no deterministic seed and
no immutable model version, so the episodes cannot be regenerated. What can be
regenerated is the eﬀect of the agent’s recorded actions on the state the oracle grades.
Replaying archived tool calls against a clean database reconstructs the terminal state
exactly, and it is what turned an inflated label into a measurable one. The precondition
is narrow and we state it as a precondition rather than as a prediction: the replay
needs a benchmark that records the agent’s tool calls in a form an external harness
can re-execute, against a database the harness can reset. We evaluated it on one
such benchmark, and Section 6 reports the independent implementation on which the
same precondition did not hold. Within that precondition it is cheap: the replay is
deterministic, needs no model, and can be cached.

Reporting a negative result, and reporting a disagreement.
Two of this paper’s findings are negative: a pre-registered mechanism hypothesis was
refuted by the ablation, and a previously reported eﬀect changed sign in a second task
domain. We report both against the interest of the narrative, and we report the first
as an explicit disagreement between an earlier mechanism account and the new data
rather than reconstructing an account that fits both. For a paper whose subject is the
trustworthiness of measurements, this is the only consistent position.

6 Threats to Validity

6.1 Construct validity

What RQ2 and RQ3 are not.
We state the boundary of the two secondary questions explicitly, because it is the
reading a reader is most likely to reach for. RQ2 and RQ3 are not measurements of
intrinsic language-model capability or behaviour. The models are the materials of the
study, not its object. What those questions characterise is the measurement process
on an audited pipeline: how design choices in the harness expose, amplify or obscure
variability that is present while a benchmark runs, and where the resulting conclusions
stop holding. The consequence for the evidence is stated in the Introduction and
carried through the paper: RQ1 is direct evidence about the evaluation system, and
RQ2 and RQ3 are reported as observations and boundaries at correspondingly weaker
strength. A reader who wants a claim about how a model behaves under localisation
will not find one here, and we do not make one.
Collapse is an operational definition: a maximal run of at least five consecutive
reply steps each spending at most two completion tokens, with no tool call. It is
mechanical and reproducible, and it is not a natural kind. The independent adjudi-
cation in Section 4.3 corroborates that the definition tracks what a reader would call
a stalled trajectory, and finds no clear diﬀerence in agreement between the language
arms; the judge is a language model rather than a person, agreement is at the ceil-
ing, and the sample is selected, so neither the corroboration nor the absence of an
arm diﬀerence is conclusive. The criterion is also defined on the agent’s token counts,

which are not a language-neutral unit of text; earlier work in this line showed that the
gap survives character-count, repetition and no-length-threshold alternatives, and we
rely on that robustness rather than claiming the token threshold is comparable across
languages. What we measure is therefore a property of the evaluated agent–simulator
configuration — how often, under this configuration, a trajectory degenerates — and
not a property of the model alone.

6.2 Internal validity

The provider exposes no eﬀective deterministic seed: at temperature zero the same
request gives diﬀerent trajectories, so the three “repetitions” per cell are a repetition
index and not a controlled randomisation, and a single run is not evidence. All com-
parisons are therefore paired within a cell and reported with task-clustered intervals.
A further internal-validity cost is that the component ablation and the second domain
ran on a platform that rebuilds the execution environment periodically; the ablation
batch consequently spans one such boundary. The elapsed gap was under an hour,
and a drift probe run over intervals an order of magnitude longer than that gap found
no evidence of version drift, but we cannot exclude it.
A larger instance of the same threat attaches to the component contrasts. The
three single-component arms were run in a single batch, but the arm that localises
all three documents and the fully English baseline come from earlier batches of this
project; the gap between the run periods is at least a day, and the provider exposes
no immutable model version, so a provider-side change between the periods is not
excluded. Pairing on task, simulator, user language and repetition removes task and
configuration variance, but it is not a within-session randomisation and cannot remove
drift common to a period. We state the consequence precisely. The existence of an
association between each component and a lower collapse rate is supported; the order-
ing of the components should be read as an observation in this configuration rather
than as an established mechanism, and the 1.11 pp contrast between localising the
tool descriptions alone and localising all three is the most exposed of the contrasts we
report. A same-period replication with the arm order reversed would settle it, and we
did not run one.
Two arms of the second experiment were dropped on the evidence of their pilot
(Section 4.2), which is a design decision made after seeing data, and we record it as
such rather than presenting the final grid as the planned one.

6.3 External validity

The auditing method has a portability boundary that we measured rather than
assumed. We applied the same suite to a second, independently implemented agent
benchmark. The attempt is a negative result: the reference terminal state needed by
the positive control could not be reconstructed from the framework’s recorded API-
call log, so no detection rate could be estimated on its held-out task set, and we
report none. The constraint is contractual rather than incidental — the framework
materialises a reference episode only inside its own run loop — and we state it as the

precondition a framework must meet before this class of auditing can be ported to it.
This bounds Contribution 1 to the implementations we actually evaluated.
The second benchmark is also one on which a record-level evidence audit has been
reported (Gao and Zhou, 2026), and the two results do not conflict. That audit asks
whether the evidence stored for a completed run supports the score the benchmark
reports, and it can proceed from records the framework already writes. Ours needs a
reference terminal state that an external harness can construct and compare against,
because a positive control must know what the correct final state is; that is the
precondition the framework did not expose. Evidence about a run and a reference
state to test the oracle against are diﬀerent requirements, and our negative result is
about the second.
All the remaining results come from one agent benchmark with two task domains,
four agents and six simulator models, all served by one provider. The trajectory-
level eﬀect is carried by one agent; the others have a zero base rate in both arms
and cannot show it, so the mechanism’s generality across models is inferred from its
mechanics rather than observed. The second domain was intended to relax this and
did not: the cross-vendor agent collapsed in none of its pilot episodes, so the arm was
dropped and independent-model validation remains open. The cross-lingual setting is
a simulator speaking Chinese against an English tool environment; other language
pairs are untested, and the simulated users are language models rather than human
speakers, which leaves open how much of the eﬀect belongs to the simulator’s language
behaviour and how much to the agent’s. Inference is conditional on the sampled tasks:
the retail results are conditional on the 30 tasks drawn from the benchmark’s test
suite, and the airline results on all 50 of that domain’s tasks.

6.4 Conclusion validity

The primary inference is a task-clustered interval, and the reference distribution is
t(G −1) with G the number of tasks, which treats tasks as the sampling unit. This
is the right unit for claims about a task suite and the wrong unit for claims about
episodes; the intervals we report are conditional on the tasks sampled and do not
absorb the sampling step. Exact tests are reported only as a cross-check and are not
used to declare an eﬀect resolved. Several of our secondary analyses — permutation,
sign-flip and task-clustered bootstrap variants — do not share a single null hypothesis
and therefore do not constitute independent lines of evidence; they are reported as
sensitivity analyses of one estimate. Finally, an interval that contains zero is reported
as no detected diﬀerence and not as evidence of no diﬀerence.

7 Conclusion

An agent evaluation harness is a piece of software, and the score it produces is an
instrument reading. We audited one such instrument and report two findings. Its
test oracle mutated the state it was grading, which inflated the recorded success rate
from 65.5% to 94.3% in our runs and would have done so silently; the mechanism is
a missing restore, the detection is a repeat-scoring or terminal-state check, and the
correction is a replay of the recorded actions rather than a re-run. The correction is

also not a uniform oﬀset: it removes between 24 and 34 percentage points from each
agent measured here and reorders the top of the matrix: the inflated score and the
corrupted comparison are two consequences of the same failure. And the language of
the apparatus is a configuration parameter of the measurement rather than a property
of the model: localising the agent’s own world is associated with a change in the
rate at which trajectories degenerate, each of the three documents the agent reads is
associated with a lower rate when localised alone in the tested configuration, and the
eﬀects do not combine additively. The relative size of the three is an observed ordering
in this configuration, not an established mechanism. The sign of that eﬀect does not
survive a change of task domain. A score table that reports neither the instrument’s
failure rate nor the configuration it was taken under is reporting less than it appears
to.
